A custom mode is a snapshot of the mode it started from (#1946, owner decision 2026-11-18 A). Its `base` no longer has to be a mode the brand generates, so turning Dark off while a custom mode started from Dark is taken instead of refused. A custom mode reads only its own `surfaces.<name>` (the schema now accepts `surfaces` keyed by a custom mode), never its base's: before, a dark-based custom mode followed `surfaces.dark` live. Since the schema takes any `surfaces` key, `brandTheme` refuses one that is neither `light`, `dark` nor a declared custom mode, naming it. `base` stays as the record of where the mode started and the appearance it derives with. No emitted token name moves. `PERSIST_VERSION` goes from 2 to 3 (owner decision O2 A, 2026-11-19): a v2 saved blob is migrated on read, not refused, copying `surfaces[base]` to each custom mode with no `surfaces[name]` of its own, so a brand saved before this change keeps each custom mode's page. A v3 blob is never migrated. A design.md tells its age the same way by a key (owner decision 5b C, 2026-11-21): `toDesignMd` always writes `surfaces.<name>` for every custom mode (`{}` where it has none), and `parseDesignMd` gives a custom mode with no such key, from a file written before this change, a copy of its base's surfaces. A key that is present is taken as is.
