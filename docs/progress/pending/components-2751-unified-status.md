## (2026-10-15) — Unified errors: Checkbox, Switch and Radio take the fields' status axis (#2751, owner Q354)

**Status:** eight defs reshaped, a new `COMPONENT_RENAMES` kind, the skill's idiom, and the tests. ENGINE minor (change note). CONTRACT unchanged: no new token, only existing roles (`color.border.danger`). No executor code moved (`apps/plugin/src` is untouched), so `EXECUTOR_REVISION` stays where main has it.

**What it builds (the approved wireframe, recorded on #2706):** Checkbox control and Switch control drop the `error` state for a `status` axis `[default, error]`, orthogonal to the states. Radio control gains it, and its header records that the Radio group sets it. The three Rows gain `status` and `follow` it into their control. Checkbox group and Radio group gain `status`, `follow` it into all eight rows, and nest a FieldMessage under the options, gated `presentWhen: { status: ['error'] }`, its own status following the group's. Every def carries the fields' `validation` prop over the first two values; the groups also carry `validationMessage`. Members: Checkbox control 54 → 90, Switch control 24 → 40, Radio control 30 → 60, the three Rows 3 / 2 / 3 → 6 / 4 / 6, both groups 3 → 6.

**The diagnosis that made the paint small:** the obvious status template, `{status}.{slot}.{state}`, has the arity of the controls' `{selection}.{slot}.{state}`, and the paint-key validator reads each key through every template of its length, so `error.border.rest` reads as `selection=error` and `unchecked.border.hover` as `status=unchecked`. The fields met the same trap and kept their two vocabularies at different lengths. So the controls' status template is four segments, `{status}.{selection}.{slot}.{state}`, bound per selection and per non-disabled state (12 keys on Checkbox, 8 on Radio and Switch). Verbose, and it states exactly the old per-selection `*.border.error` bindings, one per state.

**The diagnosis that made the migration small:** the update already matches members by coordinate, applies the declared renames, then gives every member an axis the plan added at the plan's first value. What it could not say is "this value left its axis for another", so a `state=error` member would have landed on `status=default, state=error`, a coordinate the plan no longer has, and been marked deprecated, breaking every placed error instance. One ledger kind, `move` (`state=error` → `state=rest, status=error`), applied after the renames in `renameCoordinate`, claimed in `unaccounted`, and checked in `danglingTargets`, is the whole change. The update itself is untouched: it reads the ledger, and the status axis then already exists on the moved member, so the added-axis default skips it.

**Owner items (recommendations built, flagged for the owner):**
1. **The code prop is `validation`**, the field family's name, over `[default, error]`; the groups add `validationMessage`. For Switch row the value is an outcome failure (a change that did not take), not a validation result; the prop name is shared anyway, and its description says what `error` means there.
2. **The groups' message shows only at `error`** (`presentWhen`), so a valid group looks exactly as before. Showing the same part at `default` as group helper text is the deferred group `description` (#1698 decision 3), still the owner's.
