## (2026-11-03) — Studio and plugin: the Action palette select offers Neutral (#3365)

**What was wrong.** The Action palette select offered Primary and the brand colors, never Neutral. The engine has always accepted `actionPalette: 'neutral'`: `theme.ts` checks the lever against every defined palette, and `neutral` is always one (the `t-red` corpus brand already builds that way). The gap was one deliberate line in `apps/studio/src/levers/controls.ts`, kept by #1835 until #1811 was decided (#1827, the earlier fix, was closed unmerged). The owner decided it on 2026-11-03 while settling #3336: the reference brand's buttons and links are near-black, and the owner wants to pick `neutral` directly instead of keeping a duplicate gray palette.

**The change.** `paletteRefOptions` gives every palette picker the same list: `primary`, `neutral`, then the brand colors. The plugin's UI is the Studio's, imported whole (`apps/plugin/src/ui/entry.ts`), so one line covers both hosts. The `actionPalette` lever description in `levers.ts` now names neutral and says what it leaves alone. That text is a DRAFT for the owner (Q3365.1 on the PR), and `schema/lever-manifest.json` regenerates from it. No token value or name moves for any corpus brand, so CONTRACT is unchanged. The change note declares `minor` because the manifest is a committed artifact.

**What choosing it moves.** Measured on prism3, aurora and harbor, every mode: only the action family moves. That is the primary column and its inverse, the four link families, and the two focus rings. Every other role (text, surfaces, borders, the neutral and destructive columns) keeps its hex and its alias path, and so does the neutral ramp. With no `actionAnchorStep`, an unanchored palette anchors at step 500 (`theme.ts`), so the default neutral action is a mid gray (prism3 light: `neutral.500`, 3.75:1), not near-black. A brand that wants near-black pins `actionAnchorStep` (the reference brand pins 950). Whether the Studio should offer a different default anchor when Neutral is chosen is a design question, held for the owner as Q3365.2.

**The gates.**
- `test.ts` (#3365 block): for each example brand, the same brief is built with `actionPalette` primary and neutral. The block asserts the action resolves to neutral and `interactive.primary.fill.rest` aliases the neutral ramp, that every mode contract passes, and that every role outside a literal action-family list is byte-identical to the primary build. A premise arm checks that the comparison can see a move.
- `test-lever-controls.ts`: the Action list is a literal.
- `test-chrome.mjs` §19, both hosts: the select offers Primary, Neutral, Accent. Choosing Neutral puts the primary fill's row on the neutral ramp after the redraw, and on the web host it stores `actionPalette: 'neutral'`.

**Mutations, each failing by name:** `theme.ts` mapping a neutral action back to primary; `theme.ts` darkening the neutral ramp when it drives actions (the neutral-role arm names the 100 moved roles); `modes.ts` `chromatic` taking a neutral action anchor as pinned, so nothing is nudged to its floor (the contracts arm); `paletteRefOptions` dropping neutral for the Action list (the unit test and the chrome option list on both hosts); and the select writing `primary` whatever is chosen (the chrome redraw and stored-value checks).
