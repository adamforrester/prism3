## (2026-11-15) — the part field `type` is refused off a text part, and no executor applies a text style to a non-text node (#3698 Q-PU2 A, #3783)

**STATUS: PR open, not merged.** ENGINE {{ENGINE_VERSION}} (minor, `packages/engine/changes/claude-3783-type-text-only.md`: a new run-time refusal for def authors), CONTRACT stands, `EXECUTOR_REVISION` 58 → 59 (its reach entry names no set, since no shipped def plans a text style off a TEXT node). Files: `packages/engine/component-schema.ts` (`type` moved from `PartBaseKey` to `TextKey`, a `KIND_ONLY` row, the field doc), `packages/engine/anatomy-figma.ts` (the projector guard, the paste payload guard), `apps/plugin/src/write-components.ts` (the plugin guard), `apps/plugin/component-shim.ts` and the `test.ts` paste stub (no text-style setter off a TEXT node), `apps/plugin/test-write-components.ts`, `packages/engine/lint-part-union.ts` (6 new illegal probes), `packages/engine/test.ts`, `skills/prism3-build-component/SKILL.md`.

**What changed.** #3782 tightened five part fields to their kinds and held `type`, because `figmaAnatomyPlan` read it on every kind. The owner chose to tighten it too (Q-PU2 A). At the type layer `type` left `PartBaseKey` for `TextKey`. At run time a `KIND_ONLY` row refuses it on every other kind, in the same words as the other five. The read itself is now guarded with `p.kind === 'text'`, so a def that reaches the projector without the validator still plans no text style on a FRAME or an instance.

**The executors (#3783).** Each executor had its own fault downstream of that read. The paste payload called `node.setTextStyleIdAsync(st.id)` unguarded, so a text style on a frame threw a TypeError. The plugin's optional call `setTextStyleIdAsync?.()` did nothing on such a node, and the next line recorded the style as applied anyway. Both now check for the setter first, and report `<node>.textStyle -> <style> REFUSED (not a text node)` with the same string in both executors. `planTextStyles` and the spec sheet's type rows (`component-specs.ts`) read `textStyle` off the plan. The projector is the plan's only writer of `textStyle`, and a `text` part always becomes a TEXT node, so the projector guard covers both. They need no guard of their own.

**Proof.** No output change: `regen --check` is in sync, `schema/` is untouched, and the three uncommitted exports are byte-identical on main and on this branch. All 63 shipped `type` uses are on text parts. The tests are in `test.ts`. The validator refuses `type` on a shipped part of each of the six other kinds, by name. Synthetic defs (`type` copied onto a box, slot, overlay, absolute, nest and vector part, projected directly) plan no text style. A plan with a text style forced onto a FRAME pastes with the miss, not a throw. Each layer was mutated and failed by name; the commands and output are on the PR.

**Trap.** Both Figma stubs (the paste stub in `test.ts` and the plugin's `component-shim.ts`) gave every node a `setTextStyleIdAsync`, which Figma does not. That is why neither fault showed in a test: the paste call never threw, and the plugin's optional call always "worked". Both stubs now take the setter off every non-TEXT node, as they already did with `textAlignVertical`. The #3783 paste test also checks that the frame it built has no setter, so a stub that grows one back fails that test instead of passing quietly.
