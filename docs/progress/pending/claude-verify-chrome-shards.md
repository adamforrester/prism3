## (2026-10-31) — verify runs the chrome suite in CI's shards, side by side; reviewers lean on CI for the full gate list (#3216, #3183)

Owner decision Q-CI1 A. A PR paid for three full gate runs (author, reviewer, CI), and locally the chrome suite was most of each.

**Sharded chrome in `verify.ts`.** The `chrome` gate carries `shards: { env: 'CHROME_SHARD', ids, clean }`, with `ids` the keys of `apps/studio/chrome-shards.mjs`, the map CI's shards already read through `test-chrome.mjs`. The runner empties `apps/studio/chrome-record/`, starts one `test:chrome` per shard at once (each its own process tree under the gate's limit, classified as a whole gate would be), and prints one row, a PASS only when every shard passed, with a line per shard beneath it (`combineShards`; a FAIL anywhere is the row's FAIL, a SKIP anywhere without a FAIL is a SKIP, no shards is a FAIL). `chrome-shards` then reads the `shard-<n>.json` records exactly as CI's job does, including `--merge` for the end-of-run checks. `--unsharded` runs the suite whole, as before. Default: parallel, because it measured faster here with the same verdicts (numbers below).

**The shard map check.** `shardMapProblems` holds each sharded gate's ids to `ci.yml`'s `shard: [...]` matrix (hand-written, read as text: the independent side, docs/34) and to the map's keys, by name: a shard dropped, doubled, missing from CI, or missing from the map. `lint-doc-gates` drives it as arm 7, and `verify.ts` runs it before anything (so CI's `verify.ts --list` step runs it too). Mutations, each failing both by name: shard 1 dropped from verify's ids (`does not run shard 1, which ci.yml's chrome matrix runs`), shard 2 doubled (`runs shard 2 more than once`), shard 3 renamed in the map, shard 3 dropped from CI's matrix (`runs shard 3, which ci.yml's chrome matrix does not run`), the `shards` field removed (`no gate in GATES is sharded`). `combineShards` with FAIL and SKIP swapped fails its self-check by name.

**#3183, raised rather than split.** `plugin-test`'s healthy runs: 440 s (the shared machine), 708 s (this container, inside verify), 810 s (an author's machine), 1211–1292 s alone on two review machines. The 1200 s default timed healthy runs out. `timeoutS: 3500` is 2.7× the slowest, the margin point 5 already uses. Splitting would need new CI steps; CI's own step is unchanged. A self-check holds the limit above the literal 1292 s, and dropping `timeoutS` fails it by name.

**Review.** `.claude/commands/review-pr.md` and a new CONTRIBUTING §3 subsection: the reviewer relies on CI (every check green on the exact head, `gates` success) for the full list, runs locally on the PR merged with current main the gates the change touches plus its own mutations, and runs the full verify only when the merged tree differs from the head in files the change touches. Its independence now comes from mutations and reading (docs/34): a second identical run compares what CI compared. Authors still run the whole list (CLAUDE.md §4, unchanged).

**Measured, same base tree, this container (4 CPUs, 15 GB), `VERIFY_TIMEOUT_SCALE=3` before, none after:** before, the whole list in 3729 s wall with `chrome` 1755 s unsharded; after, 2705 s wall (−27%) with `chrome` 709 s as three shards side by side (666 s, 589 s, 709 s), every shard PASS, load average about 4.3 at its peak. `plugin-test` took 708 s and 727 s in the two runs. The after run also caught a real miss: `--unsharded` is a CLI flag, so `docs/public/reference/commands.json` had to be regenerated (`agent-reference` failed by name).
