## (2026-11-01) — sets built over the Figma MCP are interactive: the paste path writes the plugin's prototype reactions (#2564)

**STATUS: PR open, not merged.** Plugin only. **No engine change, no `out/**` change, no ENGINE or CONTRACT bump.** `EXECUTOR_REVISION` 45 → 46 (`lint-executor-revision` requires it, since the reaction loop moved out of `write-components.ts`). `executor-reach.json` names no set for 46, measured by `lint-executor-reach`: 60 sets × 8 arms, 0 redrawn. Files: `apps/plugin/src/reactions.ts` (`writeSetReactions`, the loop lifted unchanged), `apps/plugin/src/write-components.ts` (calls it), `apps/plugin/src/mcp-steps.ts` (a new step, `runComponentReactions`, and the `packNames`/`unpackNames` codec), `apps/plugin/mcp-paste.ts` (one `component-reactions` script after each in-scope set's last chunk), `tools/figma-mcp/plan.ts` (its result shape), `apps/plugin/test-paste-reactions.ts` (**NEW**, an arm of the plugin `test` step), `apps/plugin/README.md`, `executor-revision.ts`, `executor-reach.json`.

**The owner's call (Q238 A applied to paste, approved 2026-11-01).** A set pasted through `use_figma` gets the same reactions a plugin build gets: Rest → Hover while hovering, Rest and Hover → Pressed while pressing (or the def's `pressState`, #2428). They are unrecorded on a paste build, like everything else there, since that path writes no member stamp.

**Why no engine move was needed.** The issue's comment planned to move `reactionMap` into the engine so the engine's chunk payload could write reactions. Since #1553, though, the MCP path runs the plugin's own bundled runtime (`mcp-steps.ts`), which imports `reactions.ts` directly. So the plugin's loop became one function, `writeSetReactions`, and both paths call it: the executor after every other write, the paste runtime in its own step after a set's last chunk.

**When it runs, and what it needs.** A reaction names its destination by node id, so it can only be written once every sibling exists: after the last chunk's combine. It is a script of its own (`component-reactions`) right after that chunk, and only for a set in scope (21 defs). The plan's member names travel in it. Plain JSON was too big: the button family's 576 names are 68KB against a 45,000-character script. They are regular (`axis=value, …`, same axes, same order), so `packNames` sends one index per axis into each axis's value list: 9.5KB, lossless, and it refuses a list of any other shape.

**Trap: the first cut put the step inside `runComponentChunk`, and `test-mcp-paste.ts`'s size arm caught it.** Every chunk script grew by the reaction code's share of the bundle, and button's chunks went from a handful to 576 one-member scripts, still over budget. Each runtime step is bundled on its own and tree-shaken, so a separate step keeps every chunk script byte-identical to before. The cost is one more `use_figma` call per interactive set.

**Independent review, and what it changed.** (1) The step found its set among the page's top-level nodes, while the chunk payload searches the whole page (`findOne`). A set a designer had moved into a frame got members but no reactions. It uses `findOne` now. (2) A re-paste overwrote reactions a designer had edited. The paste keeps no record, so it can't tell an edit from a stale reaction. The conservative option is built: a member that already has reactions is left alone, the same rule the chunks apply to members already in the set. The alternative (overwrite) is an owner question on the PR. (3) A planned member the set doesn't hold was skipped silently. It is a miss now.

**The test.** `test-paste-reactions.ts` builds `tag` (squeezed into many chunks) and `code-input-cell` (press goes to `focus-visible`) twice into the component shim. One build is `applyComponentPlan`; the other is the engine's chunk payloads run through `runComponentChunk`, then `runComponentReactions` with the data parsed from the script `mcp-paste.ts` generates. Expected side, literal: 27 reactions on 18 of 45 members, 12 on 8 of 28 (the numbers `test-reactions.ts` pins), plus named reactions for named members, spelled out. Mutations, each from a `wip:` commit, each failing by name: the write removed from `runComponentReactions` → `paste path: tag … carries 27 reactions … (got 45/0/0)` and three more; the generator emits no reactions script → those four plus `… reactions script comes after its last chunk script`; the script emitted before the chunks → `… reactions script comes after its last chunk script`. The review fixes, the same way: a top-level lookup in place of `findOne` → `a set inside a frame gets its reactions`; the keep-existing rule dropped → `a re-run leaves a designer's edited reactions as they are`; the absent-member misses dropped → `a planned member the set does not hold is reported`. On the first cut (the step inside every chunk), reactions written before the last chunk read `(63 misses — … NOT WRITTEN …)`, which is why the ordering arm exists.

**Trap.** The component shim's `getNodeByIdAsync` answers components only, with no parent, so `readReactions` reads every destination as dangling. The test host answers from the page tree, parents included, as the live host does.
