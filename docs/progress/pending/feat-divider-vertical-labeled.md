## (2026-10-29) — Divider: a vertical labeled member, upright label between two lines (#3143)

Built from the #3143 proposal and the owner's Q3143.1–.7 (all A). The set grows from 6 to 7 members: `orientation=vertical, inset=none, labeled=true`. The label stays upright with a line above and below it; the root is a column (`directionWhen`, Button group's #2661 field) that hugs the label across (a new, narrow `PartDef.sizingWhen`: hug only, resolved before projection beside `directionWhen`), 68px tall (`size.xl.height`), with `space.150` (12px, density 8/12/16) between the label and each line. Docs state a 56px minimum and keep the vertical label to "Or" between alternatives. The Q3051.2 accessibility contract is unchanged, and the wrapper carries no `aria-orientation`. ### Build check 1: a bound main-axis size on a growing line
Each line now binds a thickness key per orientation on both axes, so one orientation's cross axis is the other's main axis. The offline shim records a binding but has no model of a bound size turning a filling child FIXED, and it doesn't fill a frame with no layout of its own in either direction. So it can't measure the flip, and no real host was available here. The proposal's fallback is applied anyway: the projection writes no bound size on the axis a part grows along. That write is dead where the host keeps the fill (the parent decides the length), and it would leave the horizontal lines 1px long where the host flips it. A corpus-wide plan dump before and after the rule shows only the divider's plans move, and the horizontal labeled member's plan is byte-identical to main's. **Trap:** re-measure on a live file before relying on a growing child's bound main-axis size anywhere. The rule hides the question; it doesn't answer it.

### Build check 2: the plain vertical members on update
Measured with the real update dry run against a shim file built from main's plans: the two plain vertical members change `layoutMode` HORIZONTAL→VERTICAL and the root's `itemSpacing` binding space/300→space/150 (one child, so no pixel moves). The four other members re-apply with no field difference, and the new member is added. The as-built ledger reads the set `due` for the definition until the fold, then for the engine, naming all five parts. The print is keyed by plan index, so the inserted member shifts every later plan and the reason line over-names (the label's `type` facet included).
