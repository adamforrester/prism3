## (2026-10-23) — test:chrome lands the pointer's pending move before it measures, so a tile's tooltip no longer flickers out of the font check (#2980)

`test:chrome` failed twice on CI (#2972, #2978) at "figma light|dark 380 / Figma menu open": the Agent tile's tooltip (`agent-toggle-tip`) "drew nothing" in the embedded-font check. #2962 had already moved the pointer off the tile before that state, so the move itself was not missing. It was late. Chromium holds a mouse move until the next frame and only then updates hover, while the key presses that open and walk the Figma menu are handled at once and draw no frame of their own. So the probe could still read the tile as hovered, see its tooltip drawn and mark it for the font read. A frame then landed the move, the tooltip dropped to `display: none`, and the CDP read found no fonts for it. Whether it failed was a race between the runner's frame clock and the test's round trips, which is why it passed locally.

Two changes, both in `apps/studio/test-chrome.mjs`. `measure()` waits two animation frames before it probes, so any pending pointer move lands first and the hover the probe reads is the one the font read sees, in every state. The Figma-menu state also waits until the Agent tile no longer matches `:hover` after the move, and asserts that by name, so a move that never lands fails there rather than in the font check. Nothing is excluded: a tooltip that is really drawn (the "Agent on" state hovers the tile on purpose) is still measured and held to the embedded face, and every visible label still is.

Mutation: a visible chrome label set to a device font fails "every chrome text element draws in the embedded Inter" by name.
