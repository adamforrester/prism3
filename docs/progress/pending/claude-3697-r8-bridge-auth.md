## (2026-11-12) — The agent link proves who is talking, both ways (#3697 R8)

The review's M4: the plugin never checked the bridge. Pairing (#3204) proved the plugin to the server, but the relay heard any `welcome`, and kept any `paired` token, from whatever answered on port 17331. A process holding the port while the real bridge was down could send write commands into the open file once the person switched the link on. The owner chose A: the server proves its token over a nonce the plugin sends, an unasked `paired` is ignored, and destructive commands through the mailbox carry a per-session code.

**The bridge.** Each connection now draws its own 32-byte `clientNonce` (`randomNonce`, `crypto.getRandomValues` in the iframe and in Node), sent with the pair and the hello. The server answers `welcome` with `HMAC(token, "prism3-bridge-welcome-v1:" + clientNonce)` and `paired` with `HMAC(code, "prism3-bridge-paired-v1:" + clientNonce + ":" + token)`. The relay drops a socket whose welcome does not verify, before any command is heard, and retries on the usual schedule, so the real bridge is found once it is back. A `paired` is heard only while a code went out on that socket; one whose proof fails is an impostor and is dropped, with the code kept for the real server. The `paired` proof goes one step past the decision's wording: without it, an impostor that answered while a code was pending could still hand the plugin a token it chose, and then prove that token in its own welcome. The person sees nothing new, since the prompt and its words are unchanged.

**The mailbox.** The mailbox is shared plugin data, which any editor and any plugin can read as well as write, so a code it could find in the file would prove nothing. The code is drawn at switch-on, kept only in the main thread's memory, and shown only in the panel. The person gives it to their agent, which sends it as `session`. It is in no `prism3agent` key: the link record, `status` and the results leave it out, and `session/not-in-file` checks every key. What needs it is decided from the raw envelope (`needsSession`): `apply-theme`, `run-code`, and the confirm of `prune`, `update-components`, `panels-clean` and `set-override`. Their previews, every read, and the commands that add what is missing do not. After 5 wrong codes the code is spent until the link is switched on again. At one command per poll, that leaves the inbox no way to guess it. Bridge commands need no code, since the bridge is paired.

**Owner decisions held in the PR.** The panel's line "Session code for your agent: XXXX-XXXX." is a DRAFT (`sessionLine`). So are the guide's new step and its two safety lines, and the scope of "destructive". The main thread has no `crypto`, so the code comes from `Math.random`. That is enough against guessing through the inbox, but it is not a cryptographic draw. The other option is to draw the code in the iframe.

**A plugin and a bridge from before this change don't connect to each other.** An old plugin sends no `clientNonce`, so the new server refuses its hello. A new plugin gets no proof from an old server, so it refuses the welcome. Update both together. `AGENT_PROTOCOL_VERSION` stays 1: the command and result envelopes keep their meaning, and `session` is optional.

**Mutations, each committed as `wip:` and failing by name:** the relay's welcome check removed → `server-proof/impostor` (4 arms); its paired checks removed → `server-proof/unsolicited-paired` and `server-proof/impostor-paired`; the mailbox's session check removed → `session/refused`, `session/wrong`, `session/spent`; the server's welcome sent with no proof → `server-proof/welcome` and `pair/relay`. The first mutation run crashed the arms after the first failure, so they now keep reporting after one fails.
