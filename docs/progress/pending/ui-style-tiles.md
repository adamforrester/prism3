## (2026-09-30) — UI redesign: chrome style tiles from Prism3's own tokens, three directions in light and dark (F3, F4)

**STATUS: PR open from `ui/style-tiles`, labeled DO NOT MERGE, for the owner to pick a direction.** No engine change, no emitted artifact moves, so no engine bump and no change note. `CONTRACT_VERSION` unchanged. Everything is in `docs/superpowers/ui-redesign/style-tiles/`: `build-tiles.mjs`, `tiles.src.html`, the built `style-tiles.html`, `audit-tiles.mjs` and a `README.md` with the rationales, the measured tables and the token gaps.

**What it is.** The owner's v4 review (F3, F4) asks for two or three small directions for the studio and plugin chrome, each in light and dark, before v5. The tiles hold the same content in every direction: the top bar, the levers panel (segmented domain tabs, the Namespace field in Brand › Identity with the proposed reserved-name flag, a color field, Density chips, an "Auto: follows light" select, a slider with named stops, a switch, a "Per mode" disclosure), a 20-step ramp whose swatches fill their cells, a role row with a contrast badge, and the Activity drawer collapsed and open. A is **Quiet panels**, B is **Flat and dense** and C is **Inset fields**. A switcher covers direction, theme (Light, Dark, System) and width (1280, 380).

**The chrome is built from the default theme, not written by hand.** `build-tiles.mjs` merges `prism3.tokens.json` with its dark overlay per mode, resolves aliases, and emits `--p3-*` properties for each theme from one role mapping. The tile CSS may only reference those. The build fails on a raw hex, color function, length or duration in the tile CSS or an inline style; on an undefined or unused variable; on a chrome color that resolves through the primary or accent palette or a brand, link or focus role; and on a declared pair under its floor. Each arm was mutated and fails by name.

**Contrast is measured on the rendered page, separately from the build's declared pairs.** `audit-tiles.mjs` renders all 12 states in Chromium and checks every visible text node (4.5:1), every marked edge, fill, glyph and selected indicator (3:1), the focus ring at every Tab stop (3:1) and every hit target (24 × 24). All 12 pass. The tightest numbers are `text.secondary` on the gray ground at 4.54:1 in light and a field edge on the gray ground at 3.17:1 in light. The audit was mutated by pointing the field edge at `border.primary` in the tile CSS, which the build's declared pairs do not see, and it fails naming each field.

**The token set lacked eight things a chrome needs, and the README lists them rather than inventing values.** The two that shape the choice: `color.border.focus` resolves to the brand, so the tiles use `interactive.neutral.border.rest` for focus; and there is no raised-surface role, so A's panels sit a step darker than the ground in dark. The others: radius roles stop at 6px, so 8px and 12px come from dimension primitives; `interactive.neutral.fill.selected` equals `fill.rest`; `text.tertiary` misses 4.5:1 on every surface; there is no tinted field-fill role; there are no layout tokens for a panel width; and shadows carry the theme's tint. Whether any of these becomes an engine role is the owner's call.

**A trap for whoever re-measures this.** A soft fill cannot be the 3:1 boundary by itself. Against white, the lightest neutral that clears 3:1 is `neutral.400` (3.28:1). C therefore keeps a 2px bottom edge on fields and a hairline on chips. A future direction that promises "no borders, fill only" needs a mid-gray fill, not a tint.
