## (2026-10-14) — Release notes per engine version, generated at each fold and checked against git (#2650)

**What it is.** Owner decision Q308.1 A: plain-language "What changed in <version>" notes, generated rather than written. `packages/engine/release-notes.ts` reads four committed records at the previous fold and at this one — the Figma sets and their variant properties (`schema/component-axes.json`), each set's surface digest (`schema/component-surface.json`), the coded components (`out/components/components.ai.json`) and the guaranteed token names (`schema/token-contract.json`) — plus `COMPONENT_RENAMES`, and lists every change as breaking, new or fix by docs/30's rule widened from tokens to every name (docs/30, "Release notes"). The folded change notes follow verbatim under "In detail". `fold.ts` now writes `docs/public/releases/<version>.md` and `.json` and the version's entry in `index.md` and `index.json`, before its regen and again after it, so the notes describe the tree the fold commit holds. The plugin's Update check adds "What changed in <version> for these sets", the version's breaking and new Figma items for the sets it would change, read from the bundled `index.json`.

**The diagnosis that made it small.** Nothing new had to be recorded: every fact the notes need is already a committed record that a PR moves and a gate guards, so a release is a diff of files at two commits. The two commits are found from `version.ts` in git history (the single-parent commit that set each version: its fold), which is ground truth on `main` and needs no stored state.

**The gate.** `lint-release-notes.ts` re-derives every release from git with its own code and never imports the generator (docs/34 shape 2). Mutations, each on a synthetic fold that removes a Figma value, so the release carries a breaking item: one breaking item dropped → `BREAKING CHANGE MISSING`; a fake breaking item added → `CLAIMED, NOT IN THE DIFF`; a removal classified as a fix → `MISCLASSIFIED`; a line dropped from the page only → `MARKDOWN`; the newest release deleted → `REPRESENTED` and `INDEX`. A fold run by the old `fold.ts` (with no notes) fails `REPRESENTED`.

**Review round: what the first gate let through.** Independent review found three holes, each now closed in the gate (the generator is unchanged). (1) `TEXT` checked only that a sentence *contains* its names, so a hand-edit that reversed one (`` `select`: `state` lost its value `focus-visible-filled`. ``) passed every arm, `MARKDOWN` and `INDEX` included, because the page, the JSON and the index all agreed. The gate now restates, per kind, the phrase its sentence must carry (`SAYS`: `value-added` must say "has a new value", `value-removed` "no longer has the value", and so on), with code spans stripped so a name never supplies the phrase, and refuses a phrase that belongs to another class (`NOT_IN`). `SAYS` restates the generator's templates, which are an open owner item, so rewording a template moves `SAYS` in the same PR; that is the point of restating it. (2) The date was checked only for agreement between the index and the release; it is now bounded by git as `DATE`: no earlier than the base fold's commit day, no later than the version's own fold commit day, or today for a fold not yet committed, all in UTC, as `fold.ts` writes it. (3) A shallow clone reported its missing history as `CLAIMED, NOT IN THE DIFF` and `NOTES … (unreadable)`, blaming the notes. The gate now checks `git rev-parse --is-shallow-repository` first and stops as CANNOT RUN, naming `git fetch --unshallow`.

**Second review round: a merge read as a fold.** Both the generator and the gate first took each version's fold from `git log --first-parent -G 'ENGINE_VERSION = '`. With `--first-parent`, git diffs a merge against its first parent, and on a feature branch that merged `main` across a fold that parent is the branch, so the merge commit itself read as the 0.237.0 fold. The notes generated on the branch then missed every change note `main` added after the branch's last sync (28 of 29 here), and CI's view (`refs/pull/N/merge`, whose first parent is `main`) rejected them; notes generated from `main`'s side passed CI and failed a local verify instead. No set of files passed both. The fix rests on `main` being squash-only: every fold is an ordinary commit, so a merge is never a fold. The generator walks the whole history with `--no-merges`; the gate, written separately, prints each record's parents and skips any with more than one. On `main` the two walks give the same 228 versions as the old first-parent walk, so no committed release moves. The same round closed a nit: a `token-added` sentence's type word was not checked (`/is a new .*token/`), so a dimension token called a color token passed; the gate now reads the type from the contract at the fold, and checks a retyped sentence's from and to in order.

**Trap found while building it.** The first fold integration computed the notes before `regen.ts`. A committed artifact that disagrees with the code (here, a hand-edited `components.ai.json` in the synthetic fold) is rewritten by regen, so the notes described a tree the fold commit did not hold, and the gate caught it as `CLAIMED, NOT IN THE DIFF`. The fold now writes them again after regen.

**Backfill.** 0.234.0, 0.235.0 and 0.236.0, from git. 0.233.0 and earlier are refused: `component-axes.json` did not exist at the 0.232.0 fold, so those diffs cannot be read reliably. The current pending batch becomes the first release a fold writes; `release-notes.ts --pending` prints it now (0 breaking, 29 new, 1 fix).

**What the next fold does differently.** Nothing by hand: `fold.ts --dry-run` prints the counts and each breaking item, and `fold.ts` writes the four files. A fold branch that merges `main` runs `release-notes.ts --refresh`, because the range then includes `main`'s newer record changes. The open fold PR from before this change (#2582) has no notes and fails `REPRESENTED` once this lands, so it is refolded on top.

**Limits.** Figma's boolean, text and instance-swap properties are in no baseline, so a change to one shows only as "builds differently". A coded prop rename has no ledger, so it reads as one removal and one addition, which is the right class but not paired. The plugin shows the notes for the version it builds at only, not for every version since a set was built.

**Merging #2644.** The agent reference (`emit-agent-reference.ts --check`) requires every file that reads `process.argv` to be listed as a CLI or excluded with a reason. `release-notes.ts` is a hand-run entry point (`--pending`, `--version`, `--refresh`), so it joins `CLI`, and `docs/public/reference/commands.json` lists its usage and flags.
