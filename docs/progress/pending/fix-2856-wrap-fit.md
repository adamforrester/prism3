## (2026-10-20) — Style guides: a group you made that wraps fits its widest row, not one long row (#2856)

The copy-file run after #2827 doubled the width of the owner's groups on the semantic-tokens page: Semantic colors 15160 → 30994, Borders 2427 → 4690 (its first guide moved up beside the header), Fonts 4759 → 9354, Space & size 4890 → 9392. Those frames are HORIZONTAL auto layouts with wrap on, FIXED wide: the `_section-header` takes the first row and the guides wrap below it.

**The diagnosis.** #2827's never-clip rule, `fitToContent` in `apps/plugin/src/style-guide.ts`, summed a HORIZONTAL frame's children along its axis, as if they sat on one row. For a wrapped frame that sum is the header plus the guides plus the padding: wide enough for both to share a row, so the guides moved up beside the header. #2827's fixture (section 39) had wrap off, so it passed.

**The fix, reusing #2827's code.** `fitToContent` keeps its shape: the same in-flow child filter, the same FIXED/HUG reading, the same never-shrink rule, and the same restore of a hugging axis after `resize`. Its one-row sum is now the `oneRow` helper, used as before for a frame that does not wrap. A frame with `layoutWrap: 'WRAP'` needs only its widest non-FILL child plus its horizontal padding across. Its height is its rows at the width it ends at: each row as tall as its tallest child, with `counterAxisSpacing` between rows (`itemSpacing` where the host leaves it unset), plus its vertical padding. The overlap and push-down passes after it are unchanged.

**Frames the bad run already widened.** #2827 stores nothing on a frame it resizes: no plugin data, no record of the width before. So the only sign of its widening is the width itself. A wrapped, FIXED frame that is exactly the old one-row sum of the children it holds now (to the half pixel), and wider than its widest row needs, goes back to the widest-row width. Any other width is taken as the owner's and kept. The width from before the bad run cannot be recovered, so the widest-row width is the target: it is the narrowest width that does not clip, which can be wider than the original (Semantic colors' 15160 clipped its 15676-wide grid). This is a guess about where a width came from, so it went to the owner as an Owner question on #2856. A is built; B removes the `widened` line.

**The trap for re-verifying it in the file.** The match uses the child widths of the current run. If a guide's width changed since the bad run (tables added or removed), the sum no longer matches and the frame is left wide for the owner to fix by hand. That is the safe failure.

**The test.** Section 40 of `test-style-guide.ts` builds a wrapped owner frame: padding 240, 48 between items, 96 between rows, an owner `_section-header`, and the drawn Guides grid. The shim gained its own wrap layout (`wrapRows`: x positions and the hugged height), written from the host's rule and not from the plugin's. The expected width is the rule itself, padding + widest child + padding, typed in the test. The cases: a clipping frame grows to 36127 and not the 70984 one-row sum, the grid stays on its own row, and the height is two rows 96 apart; a frame set to the one-row sum is put back to 36127; a frame 1000 wider than that sum is kept; each rerun moves and resizes nothing.

**Mutations, failing by name.** With the wrap branch dropped from `need`: "40: a wrapped frame you made grows to its widest row…" fails, and so do the height check and "40: a wrapped frame the one-row sum widened is put back…". With the repair disabled (`widened` forced false): "40: a wrapped frame the one-row sum widened is put back…" fails.
