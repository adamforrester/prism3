## (2026-11-01) — the CLI paste path migrates renames through the plugin's own rename pass (#1024)

**STATUS: PR open, not merged.** ENGINE {{ENGINE_VERSION}} (minor, `packages/engine/changes/claude-1024-paste-rename-migration.md`), CONTRACT stands. Files: `packages/engine/rename-map.ts` (the apply functions, moved in), `packages/engine/rename-runtime.ts` (**NEW**), `packages/engine/materialization-renames.ts` and `packages/engine/figma-names.ts` (one source exporter each), `packages/engine/materialise-to-figma.ts` (the `migrate` pass), `packages/engine/package.json` (one export), `apps/plugin/src/write-figma.ts` (calls the engine), `apps/plugin/test-rename-parity.ts` (**NEW**, an arm of the plugin `test` step), `docs/10-figma-materialization.md`.

**What was wrong.** One rename had two outcomes. The plugin executor moved a renamed variable in place (#1013), keeping its id and every binding. `materialise-to-figma.ts` was create-or-update-by-name, so it created the new name beside the old one and orphaned every binding. Nothing compared the two paths, so nothing saw it. The MCP paste bundle (#1553) never had the gap: it bundles the plugin's executors. This was the hand-written CLI path only.

**The fix shares the code instead of copying it.** The apply half of the pass (`beginMigration`'s validation and atomic collection pre-pass, `upsertCollection`'s variable renames) moved from the plugin into `rename-map.ts` as `openMigration` / `renameCollections` / `renameVariables`. The plugin calls them. The paste payload can't import, so it ships their source (`Function.prototype.toString`, the move `nestVariantMatchSrc` already makes) and calls them in the file, in a new first pass, `migrate`. The materialization rules ship the same way, with the three constants they close over serialized from the constants themselves.

**Two traps in shipping source under tsx, both found by running the payload.** (1) A reference to an IMPORTED name compiles to `(0, import_x.name)(…)`, an object the payload doesn't have. So every shipped function may call only functions in its own module: that's why the apply functions live in `rename-map.ts` and take `root` as an argument rather than calling `rootOf`. (2) tsx wraps a nested named function in `__name(fn, "…")`, a helper it injects at module scope. The runtime defines an identity `__name`.

**Size.** The map is ~21KB and the colour axis's planned names ~11.5KB, so the pass is packed by bytes per axis, like `color-create`. Planned names travel as tails under one root per axis, and contract rows as `[from, to, since]`. Today every axis fits one payload (41.7KB for the reference brand). Every chunk re-runs the collection pre-pass, which is a `source-absent` no-op after the first, so chunks are order-free.

**The gate.** `test-rename-parity.ts` seeds one old-names file and materializes it twice into `file-shim.ts`: by `beginMigration` + `applyWritePlan`, and by the paste path's real `migrate`, `palette` and `color-create` payloads. The expected side is six literal old → new pairs plus the collection rename, each checked against the register that states it (a `COLLECTION_RENAMES` entry, a `DEPRECATIONS` row, or a materialization rule). Variables are followed by id, so a path that recreates instead of moving fails. Mutations, each from a `wip:` commit, each failing by name: the `migrate` pass removed → `paste path: every old name in the fixture is MOVED` and 3 more; its `renameVariables` call dropped → the same arm plus the report arm; the plugin's `renameVariables` call dropped → `plugin path: every old name in the fixture is MOVED` and the parity arm.

**Not changed.** The pre-#1097 un-rooted `core` names are still invisible to both paths (#1109): the parity is exact, including that gap.
