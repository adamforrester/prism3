## (2026-11-02) — Update file's run goes on past sets built with problems (#3308, fix 2)

**The defect.** The owner's first run stopped at To add: "Stopped at To add · Built 9 sets · 5 with problems", "1 failed", and the style guides never drawn. Reproduced in the component shim under `fixHostMethods`, driving the plugin's real `main.ts` with the panel's posts: every one of the nine sets completed. Five (Button, Checkbox.Row, Checkbox.Group, Link, Badge) were "built with problems" for one reason each: "No usage panels drawn: this file has no _Doc-block component" (Set up file, the run's first step, cannot build `_Doc-block` until Badge, Tag, List item and Divider exist). Nothing failed. The run stopped because the sets step's verdict was the queue's `runVerdict`, whose `ok` is false for any set with problems, and `stepDone` ends the run on any step that is not ok. And Activity counted it a failure because the queue's headline had no "⚠" (D-RED A reads a warning by that mark).

**The fix.** A step result can be `warn`: not ok, but it did all it was asked. `stepDone` (`state/update-file.ts`) goes on past one. `main.ts`'s sets step marks itself `warn` when every queued set has a result and none failed (one set: `completed`). A failure or a stop still ends the run. `stripVerdict` (`state/status-strip.ts`) does not take a `warn` step for where the run stopped; the finished line becomes a warning, "File updated", with the step's own words after the steps. `runVerdict` (`state/build-queue.ts`) marks "Built n sets · k with problems" with "⚠" when nothing failed and nothing was left, as a single set's own "with problems" headline is, so Activity counts a warning.

**What this does not do.** Why each set had problems is #3308's other half (the reasons, a DRAFT Q-block), and the `_Doc-block` sequencing and the cover not drawn on a first run are held for the owner there. The theme step's own "⚠ n misses" still stops a run, unchanged.
