## What this repo is

An npm-workspace monorepo for the **Prism3 design-token engine** and its surfaces. Knowing which layer you're in decides almost everything:

| Layer | What it is |
|---|---|
| `packages/engine/` | The **engine** — dependency-free TypeScript, run via `tsx` (**no build**). Generates the token layer from a small brand input. Consumed by name as `@prism3/engine`, never by relative path. Start here for engine work. |
| `packages/tokens/` | The **consumability gate** (`@prism3/tokens`) — a stock Style Dictionary over the emitted DTCG, proving the output is consumable without custom code. |
| `apps/studio/`, `apps/plugin/` | The two **surfaces** that bundle the engine (`@prism3/studio`, `@prism3/plugin`). These build. |
| `apps/tokenpress/` | **TokenPress** (`@prism3/tokenpress`) — the Figma plugin that exports Figma variables/styles *out* to DTCG, i.e. the opposite direction from the engine, and the one surface here that ships publicly in the Figma Community. Ported in whole (copy first, adapt second), so it does **not** follow this repo's patterns inside `src/`: its own DTCG emitter, its own alias resolution, no `@prism3/engine` import anywhere. Treat it as a guest — read `apps/tokenpress/README.md` and its own `agents.md` before editing, and do not "align" it with the engine on the assumption the duplication is accidental. It is measured, not accidental. |
| `docs/` | The **design record** — the numbered design docs plus `superpowers/` working notes. |
| `skills/` | The **product skills** — `prism3-theme` (authoring a brand) and `prism3-consume` (building UI from generated tokens), addressed to an agent working *with* Prism3. Shipped prose that makes factual claims about the engine, so `lint-skills.ts` gates them. Per-brand *payload* skills, addressed to an agent in a client's ejected repo, are emitted by the engine (#668) and do not live here. |
| `reference/` | The **legacy hand-built token JSON** — Prism2 + New Balance. Read-only in practice: it is the engine's regression target, not a place to author. |
| `tools/` | **Measurement harnesses** — runnable and committed. `tools/exporter-comparison/` runs prism3's DTCG emitter and TokenPress's over the same brand and classifies every difference (#697's Verify bullet). A tool here answers a question; a gate asserts an answer, so the two live in **separate files**: `compare.ts` reports all five categories and always exits 0, and `gate.ts` — the assertable subset, in CI — fails on the seven arms where a difference means one exporter is *wrong* rather than *different*. Its third file, `axes.ts`, is neither: it is #697's recorded **decision** about which collections' modes are an axis, wired in so mislabeling one fails a gate rather than sitting in prose. Don't promote a category without deciding it is a *defect* rather than a documented disagreement; the ones left out are named in `gate.ts`'s header, with why. `tools/nest-exposed-cost/` measures what a `nest-exposed` nested part would cost the parent that exposes it (#681) — panel rows against Figma's ceilings, and payload bytes through the real chunk packer. It has no gate sibling on purpose: nobody has decided what the ceiling ought to be, so there is no answer to assert. Read its header before quoting a number from it, and know that **#761 read its own byte figure wrong and a reviewer caught it**: worst-chunk fullness is near-budget *by construction* (`pack` fills until the next variant will not fit) and chunk overflow is absorbed by adding chunks, so "4 bytes of headroom" was an artifact, not a cliff. The ceiling that means something is the **indivisible unit** — shell + largest single variant, since no re-packing can split one variant across two calls — which is at 49% of budget on the largest real set. The generalizable trap: an instrument found non-monotonic is disqualified for *every* reading taken from it, not just the one that prompted the check. `tools/forward-claim-check/` finds present-tense claims about *mutable* issue state in tracked prose (`blocked on #N`, `#N is still open`, `parked pending #N` — written schematically here on purpose, see below) and reports each against the state the cited issue is in — a small fraction of the repo's issue citations qualify as reportable sites (see the file's own header for the live count; a hardcoded snapshot here would go stale the same way the claims it detects do). Also **no gate sibling, for three independent reasons, strongest first**: **the misses cluster on the issues it already catches** — one issue is caught at a single site and claimed at six more in words no pattern covers, so a gate goes green the moment somebody fixes the one sentence it named, which is shape 9 producing *evidence-shaped output rather than silence* and holds **even at 95% recall**, since it is about the distribution of the misses rather than their count; **recall was measured once at 11.0%, 95% CI [5.8%, 15.2%]** — a **dated snapshot, not a live figure**: `recall-snapshot.mjs` carries the counts, re-derives the interval from them, says plainly what does *not* reproduce (the frame generator was not kept, and 32% of the roster sites have already moved or gone), and **checks its own expiry against today's reportable count — a check that already fires**, since the guest exclusion moved a site out of the numerator days after the measurement. Quote it with its date and its drift, never bare. It is an upgrade on the earlier "the denominator is unknown" rather than a correction of it, and a finite number invites *"so raise it"*, which is why it does not lead; and **the error costs are asymmetric**, since a missed stale claim is the status quo while a false STALE at full confidence is worse than having no tool at all, because someone "fixes" a sentence that was right. A gate here would report clean over everything it cannot see — `docs/34` shape 9. It exits non-zero **only when the instrument is broken** (zero citations, a corpus below the recorded baseline, a pattern that stopped firing on its own sample, a stale register), never because a claim is stale. Its exclusions — append-only dated journals, vendored guest sub-projects (a guest's `#N` names its **own** tracker, so a corpus spanning more than one issue namespace has to resolve namespace before state), and claims *quoted* rather than asserted — are properties of the **document**, not of the pattern; narrowing the pattern instead would score better and know less, and the header says so at length. Genre is only **half** of the namespace problem and the recall sample proved it: of nine foreign-namespace claims measured in the corpus, six sit inside the guest and are covered, but **three sit in our own prose, where the document is ours and only the citation is foreign** — nothing about the file marks it, and an unmarked `#N` here is *provably* ambiguous, since the same small numbers name both a guest issue and one of ours. Those three are registered, not resolved: a marker convention (`owner/repo#N`, which the guest's own source already uses) would fix citations written after it and is a house-style decision nobody has taken. **The registers are hand-maintained lists of exceptions to a low-recall detector and inherit both weaknesses** — the foreign-namespace register held one of nine until somebody measured — so read a count from this tool as a floor, never as coverage. Three artifacts sit beside `measure.ts` and back **different** claims, which is the point: `recall-snapshot.mjs` + `recall-classification-record.txt` back the recall figure, and `form-probe.mjs` backs the *clustering* argument by showing the pattern set recognizes **0 of 11** real corpus phrasings for one claim. Sixteen hand-picked sentences cannot estimate a rate — do not read a percentage out of the probe, and do not cite it for recall. Issue states come from a committed `issue-states.json` resolved via the GitHub MCP tools, so verdicts are only as fresh as that file. One hazard learned while writing that row: **quoting a live claim verbatim in a non-journal document is indistinguishable from asserting one** — this row's first draft cited a real closed issue as an example and the tool duly reported `CLAUDE.md` itself as stale. Write examples schematically (`#N`), or expect the documentation of a detector to be caught by it. |

## Prism3 — the generation engine (start here for engine work)

The engine generates the token layer instead of hand-authoring it: it reproduces New Balance from a small brand input, then generalizes to new brands. **No build, no `npm install`** — run it via `tsx`.

For any engine or token-generation task, read these first (they hold the durable state so work survives a context clear):
- `docs/00-progress.md` — status, decisions log, and prioritized next steps.
- `docs/07-e2e-journey.md` — the designer↔developer↔agent pipeline + portable-core architecture.
- `packages/engine/README.md` — how the engine works and how to run it.

The two surfaces that bundle the engine:
- `apps/studio/` (`@prism3/studio`) — the web dashboard/theme studio (esbuild dev server); see `apps/studio/README.md`.
- `apps/plugin/` (`@prism3/plugin`) — the Figma plugin (two-context split + typed postMessage bridge); see `apps/plugin/README.md`. For plugin work read `docs/18-plugin-and-host-architecture.md` (capability grounding) and `docs/22-plugin-plan.md` (the phased build plan, #106–#110).

Workflow: one PR per feature branch off `main` → squash-merge → delete branch → sync `main`.

**When more than one agent may be working, use a git worktree — not the shared checkout.** `git worktree add /tmp/p3-<lane> -b <branch> origin/main`, then give it a `node_modules` (the repo is buildless, but a fresh worktree has none, so `npx tsx` would re-download and the `apps/studio`/`apps/plugin` builds would fail). **Populate it with `npm ci` — never a bare `npm install`, and never a hand-rolled symlink loop.** `npm ci` is the whole setup: measured in a fresh worktree, 5s, and it builds all five `@prism3/*` links *relative* so they resolve inside that worktree. `install` is free to resolve a version the lockfile does not pin, and on 2026-08-11 a stray interrupted-install artifact in the shared tree let an unlocked `@figma/plugin-typings` leak into a review worktree that way. **Do not also symlink afterwards** — composing the two leaves 86 stray links in a tree whose cleanliness is load-bearing, and `never `ln -s` the whole directory` is the older hazard it replaces: workspace links are relative (`@prism3/engine` → `../../packages/engine`), so reached through a whole-directory symlink they resolve against the *main checkout*, and every `@prism3/*` import loads the code from the tree you are not working in, with exit 0 and no warning. Nor may you symlink the directory and overwrite `@prism3/*` afterwards — that writes *through* the link and repoints another session's `node_modules` at your worktree. **And once a worktree's `node_modules` is a tree of links, never point a package manager at it — not `npm install <pkg> --prefix <worktree>`, not `--no-save`, not to add a single dependency.** This is the same write-through hazard from the direction the two rules above do not name: they warn about how you *build* the links, and this is about operating *inside* them afterwards. Measured on 2026-08-14, `npm install --no-save --prefix /tmp/p3-<lane> playwright@1.62.1` — a package already pinned at exactly that version in `package-lock.json`, so the install was unnecessary before it was harmful. npm reconciles the whole tree against the `package.json` it finds, decides 292 packages are extraneous, and prunes them: the worktree dropped from **252 links to 18**, and because it unlinks *contents* rather than the link, the deletions went through to the shared checkout and emptied **12 scoped directories** there (`@esbuild`, `@figma`, `@types`, `@typescript-eslint`, `@eslint`, `@bundled-es-modules`, `@zip.js`, `@jsonjoy.com`, `@rtsao`, `@humanfs`, `@humanwhocodes`, `@eslint-community`). Every other session's builds and typechecks break, in a tree you never touched, with nothing in `git status` to show it — **no tracked file changes, so the damage is invisible to git entirely.** The repair that worked, in order: relink the worktree (238 third-party + the five `@prism3/*` **relative**, verified resolving inside the worktree, + `.bin`), then a plain `npm install` in the shared checkout, then confirm all 12 scoped directories repopulated *and* that the shared `@prism3/*` links are still relative and still point at the shared tree, then prove it by building — `apps/plugin build` and `packages/engine/test.ts`. What to do instead: if a lane genuinely needs a dependency the lockfile already pins, `npm ci` in that worktree gives it to you; if it needs one the lockfile does *not* pin, that is a `package.json` change and belongs in a PR, not in an ad-hoc install. A one-off browser download (`npx playwright install chromium`) is fine — it writes to a cache outside `node_modules`. **These three cover building the links and writing inside them; whether any other tool that walks `node_modules` in place is safe here is a question nobody has answered, so treat an unlisted one as unproven rather than as permitted** — reading a closed list out of the three above is exactly how the third one happened (`docs/32`, #849 and #852). `.claude/commands/review-pr.md` carries all of these measurements; for a review, the failure mode is a false pass. Anything that checks out a branch in a tree someone else is editing destroys their uncommitted work: `/review-pr` did exactly that twice on 2026-08-05, once auto-stashing the other session's edits and once rebasing its branch onto an unrelated PR's commits. Recovery, if it happens to you: the checkout auto-stashes rather than deletes, so `git stash list` then `git show 'stash@{0}:<path>'` extracts single files **without popping** — popping merges two PRs' work, since the stash may hold both. **That recovery is for the BRANCH form only, and says nothing about the adjacent one.** `git checkout <ref> -- <path>` — the pathspec form — auto-stashes nothing. It is spelled like *"show me this ref's version"* and is a destructive write to the working tree and the index: no prompt, no stash, no undo. So the sentence you just read is the hazard, not only the cure — a reader who has internalised it believes in a safety net that is not there one command over. **To READ a file at another ref use `git show <ref>:<path>`; to compare, `git diff <ref> -- <path>`.** Neither writes anything. **And the damage from the pathspec form is partly undetectable**: only paths that DIFFER between the ref and `HEAD` appear in `git status`, so a file with uncommitted edits that happens to be byte-identical between the two is reverted silently and reads as clean afterwards — the same invisible-to-git shape as the `npm install --prefix` incident above, and no command finds it after the fact. Three incidents in two days across two sessions, all one command shape: an orchestrator staged `main` over a branch's working tree in the shared checkout while meaning to read one file; a worker detached `HEAD` onto `origin/main` mid-check and reverted every file, losing nothing only because the work was already pushed; and the same worker, hours later, **destroyed an entire uncommitted implementation** with `git checkout -- <file>` used to reset between mutations. Two of the three cost nothing, and neither because of care taken at the moment — **push before you browse**, and every variant becomes recoverable. **The third is the one with a rule in it, and the rule is an ORDER rather than a caution: commit BEFORE the first mutation.** This repo mutation-tests nearly every gate, and the pattern's restore step *is* `git checkout -- <file>`, restoring from `HEAD` — so uncommitted work in a file you are about to mutate is destroyed by the RESTORE, not by the mutation, and it happens on the first successful iteration rather than on a mistake. Commit (a `wip:` commit is fine), then mutate, then restore, then `--amend` the real message once the run is green. Run it in the other order and the technique deletes the work it was invoked to verify. `regen --check` should report **111** artifacts; `ci.yml` asserts that number. If you see a different count, check `git status` for an untracked file under `packages/engine/out/` before assuming drift.

**A squash-merge rewrites the SHA, so a merged branch is not recognizable as merged from its own history.** Three separate races on 2026-08-12, each diagnosed correctly in isolation and none recognized as the third: a `--force-with-lease` rejected as stale after another session had rebased the branch; a first push that recreated a branch already squash-merged mid-task, instead of updating its open PR; and a correction pushed to a branch under review, orphaned when the merge took a rewritten copy of the earlier commit — the PR body carried the fix and `main` did not. Two rules follow, and both are about *content, never SHA*. **Once a branch is up for review, land a correction as a follow-up PR rather than a push to it** — a review comment arriving on merge-ready work is a race you will sometimes lose, and losing it drops the commit silently. And **before pushing to a branch you have not touched in the last hour, compare trees rather than trusting `--force-with-lease`**: the lease reads your *tracking ref*, which goes stale the moment the remote branch is deleted after merge, so it rejects on bookkeeping while proving nothing about the work. `git log --oneline origin/main..<branch>` plus `git diff origin/main <branch>` answers "is my work already in" in the only way squash-merge leaves available. If the answer is yes, reset the branch onto `origin/main` and start the follow-up there. **One concrete signal sits in the push output, and it is the only checkable thing in this paragraph: `* [new branch]` on a push to a branch you did not just create means the remote branch is gone — squash-merged and deleted — and you have recreated it, orphaned from its own PR.** `--force-with-lease` will not produce it: the lease reads your stale tracking ref and accepts. Caught this way on 2026-08-14, the first of the three races found before it landed rather than after — the push looked ordinary and `git diff --stat origin/main HEAD` showed the branch would have **reverted 784 lines across 13 files** of three other lanes' merged work, an entire new `tools/` harness among them. So when that line appears, stop and diff against `origin/main` before opening anything; the rest of this paragraph is a discipline, and this is a thing you can see.

**Carry the `docs/00-progress.md` entry in the feature PR itself**, not as a follow-up. Three PRs in a row (#306, #312, #315) merged without one and needed a separate docs PR to catch up, and the entry is worth most for exactly the things a diff cannot show: the diagnosis that made the fix small, the tradeoff that was deliberate, the approach tried and discarded, and any trap waiting for whoever re-verifies this later. Write it as part of the work, while that reasoning is still in hand.

## Two parallel token formats

Each brand contains the **same logical tokens twice**, in two formats. Edits usually need to land in both — they describe the same data for different consumers.

```
<Brand>/tokens/
├── raw-figma/   # Figma plugin export format
└── tokens/      # DTCG (W3C Design Tokens) format
```

### `raw-figma/*.json` — Figma variable export
Flat array under `variables[]`, file-scoped `$collection` + `$mode`. Colors are RGB float objects (`{r, g, b, a}` 0-1). References use `alias` + numeric `VariableID:*`. This is what Figma's Variables plugin reads/writes.

### `tokens/*.json` — DTCG format
Nested object tree (e.g. `nbds.pds.color.blueberry.100`). Each leaf has `$type`, `$value`, `$description`, `$extensions.figma`. Aliases use brace syntax: `"{pds.color.neutral-cool.850}"`. The `$extensions.figma.variableId` round-trips back to the raw-figma IDs.

When editing a value: change it in **both** the raw-figma file and the DTCG file, and keep the `variableId` linkage intact — it's how the two formats stay reconcilable.

## Mode organization differs per brand

- **Prism2** splits by appearance: `light/`, `dark/`, `wireframe/` each carry `brand-theme.json` + `motion.json`; primitives, typography, spacing, etc. live in `shared/`.
- **New Balance** splits by viewport: `desktop/typography.json`, `mobile/typography.json`; everything else (color, motion, focus, radius, layout, shadows, breakpoints, dimensions) lives in `shared/`.

Don't force one brand's structure onto the other.

## Naming conventions

- Prism2 tokens are namespaced `nbds.pds.<category>.<...>` — preserve this prefix.
- Token slugs in DTCG paths use kebab-case for words, dot-separated levels, with numeric scale steps as keys (`blueberry.100`, `blueberry.150`).
- The Figma exports use slash paths (`pds/color/blueberry/050`) — the `0` padding (e.g. `050`) only appears in raw-figma; DTCG drops it.
- **US English** in all *visible UI text* and all *emitted artifact prose* (`out/**`, the emitted `schema/*` files, the generated reports): `color` not `colour`, `gray` not `grey`, `-ize` not `-ise`. **Enforced, not remembered** — `npx tsx packages/engine/lint-us-english.ts` gates every shipped surface and runs in CI *after* the web build (its scope covers the built bundle). Scope is imported from `regen.ts`, so a new emitted artifact is covered automatically; `schema/token-contract.json` is deliberately *not* a regen artifact (see principle 5) and so is named by hand in the gate — anything else kept out of regen needs the same line, **in this gate *and* in `lint-voice.ts`, and that is now asserted rather than remembered** (#807). `lint-schema-classification.ts` fails until every file in `packages/engine/schema/` is classified: regen-covered, hand-named in **both** prose gates, or exempt with a stated reason. The rule above had been performed by memory, and three files — `payload-manifest.json`, `nb-measured.json`, `theme-schema.example.json` — were in neither gate with nothing recording whether anyone had decided. Note what made that invisible: two files in the *same directory*, one covered and one not, are indistinguishable from outside, which is exactly the membership-by-location defect `payload-manifest.json` itself exists to remove one tier down. **A false positive is fixed by adding to `NOT_EN_GB`, never by narrowing a scan.** Code comments and identifiers are exempt, *except in `apps/studio/src`*: which comments esbuild keeps in the bundle is an implementation detail, so an exemption the gate cannot see is not enforceable — write US English in `apps/studio/src` comments too. **Boundary, stated because it is open rather than decided:** that reasoning covers *any* module that can reach a bundle, not just that directory, and `packages/engine/components/*.ts` can — one import made `icon.ts` reachable and turned two long-standing comment spellings into shipped text (#849). **58 en-GB instances across six component defs are latent behind it**, and whether the carve-out extends to them is a question this paragraph does **not** answer; #849 holds it. Read the silence as undecided, not as decided in your favor. The four traps this gate encodes, each of which caught a previous pass, are documented in the file's own header; read it before touching either scan.

- **Voice.** All shipped prose follows `docs/voice-standard.md` — the operative rules (four voice attributes, a banned-phrase list, per-channel register, tone by situation, a 5-question pre-ship check). It is short and self-contained by design: read it before writing UI strings, lever/role descriptions, emitted `$description` prose, `.ai.json` fields, READMEs, or marketing copy. The reasoning behind it is `docs/29-tone-of-voice.md`; change the standard only by changing that. Two things to know going in: **most Prism3 prose is generated, not typed**, so applying the standard usually means editing `levers.ts` or `ai-metadata.ts` rather than a string; and the load-bearing attribute is **recessive** — Prism3 builds *other people's* brands, so in every product surface the tool's voice must not compete with the brand on screen (this is why we don't borrow the confidence about personality that first-party systems like Polaris or Material can afford). Code comments are exempt, same carve-out as US-English.

## Working principles (agent behavior)

Adapted from the Karpathy coding guidelines (github.com/multica-ai/andrej-karpathy-skills). The point is to turn imperative requests into declarative goals with verification loops.

1. **Think before coding.** State assumptions explicitly; surface ambiguities and tradeoffs *before* writing code. When a choice is genuinely the user's to make, ask — don't guess. (This project runs as a design dialogue; decisions get confirmed before they're built.)
2. **Simple implementation, rigorous correctness.** Write the minimum code that solves the request — no speculative abstractions or features beyond what was asked; stay dependency-free (own the math, don't pull libraries). BUT this is an accessibility / design-system domain: hold the *correctness* bar high — contrast contracts, field research (the knowledge-base + NB/Prism2 examples), and "better than the examples" are the standard, not gold-plating. Simple code, rigorous contracts — the two are not in tension.
3. **Surgical changes.** Edit only what the task needs; don't refactor adjacent code or fix unrelated pre-existing issues unless asked. One concern per PR. Preserve existing patterns, naming, and conventions. **"One concern per PR" stops you fixing a defect you found but weren't asked to fix — it does not stop you filing it.** Noting it in the PR body or a `docs/00-progress.md` entry is not filing it: prose in a write-up is not discoverable as work, doesn't get a label or a lane, and strands the defect for whoever next reads that entry to rediscover independently. Before moving on, file it as its own issue, citing where it was found.
4. **Goal-driven execution with verification.** Define verifiable success up front and loop until green. **Before pushing, run the whole list below — never a subset chosen because the diff "only touched the engine."** CI runs every one of these on every PR regardless of which files changed, so a documented checklist shorter than CI's is one a diligent contributor can follow exactly and still ship broken. That is not hypothetical: two independent PRs each shipped a "gates all pass" table built faithfully off a list that had gone short, and both broke a gate it omitted (`lint:classes`, since retired in #770 — the *list* going short is the durable lesson, not the particular gate).

   - **Run them with `npm run verify`** (`verify.ts`, #789) rather than by hand — it runs every gate below in a declared, checked order and prints a per-gate PASS/FAIL table. What that buys, in short: the exit status is captured with **no pipeline between** the command and the check (a piped read can report the wrong step's status); output is buffered per gate, so a clean run is a table and a red run is a table plus only what failed; it **enforces the ordering** below and refuses to run if the array violates a gate's own declared `after`; and it **never prints a pass for a gate that did not run** — SKIP is not a pass, and a table shorter than the list is itself a failure. Its list is the **fifth** authored statement of the gates, checked against `ci.yml` in *both* directions by `lint-doc-gates.ts`. Full rationale for all four properties, and for the runner's own design, lives in `CONTRIBUTING.md` §3.
   - **Engine** — run `npx tsx packages/engine/regen.ts` first (regenerates every committed artifact), then confirm: `regen.ts --check` · `test.ts` · `mcp-test.ts` · `token-contract.ts --check` · `lint-skills.ts` · `nb-regression.ts` · `lint-doc-gates.ts` · `lint-layout-claims.ts` · `lint-decisions-index.ts` · `lint-context-nodes.ts` · `lint-progress-order.ts` · `typecheck-components.ts` · `lint-payload-manifest.ts` · `lint-overlay-completeness.ts` · `lint-paint.ts` · `lint-rung-names.ts` · `lint-shape-index.ts` · `lint-schema-classification.ts` · `lint-absolute-inset.ts` · `lint-standalone-floor.ts` · `lint-glyph-geometry.ts` · `lint-advisory-expiry.ts`, plus every DTCG alias resolving and every mode contrast contract passing.
   - **Web** — `npm run -w @prism3/studio` → `typecheck` · `test` · `build` · `test:smoke` (run **after** `build` — it drives the built `dist/main.js`) · `check:ignore` · `lint:contrast`.
   - **Plugin** — `npm run -w @prism3/plugin` → `typecheck` (both contexts) · `test` · `build` (`dist/main.js` must carry 0 `node:` builtins) · `test:verdict` (run **after** `build` — it drives the built `dist/ui.html`).
   - **TokenPress** — `npm run -w @prism3/tokenpress` → `test` · `build`. **No `typecheck`** — its `tsconfig.json` mis-wires `@figma/plugin-typings`; pre-existing, out of scope for the port, tracked as a follow-up. Do not add the step until the tsconfig is fixed, or you will just be pinning 232 errors.
   - **Exporter agreement** — `npx tsx tools/exporter-comparison/gate.ts`, run **after** the TokenPress build — it executes TokenPress's real `TokenExporter` in memory over prism3's own Figma emission.
   - **Tokens** — `npm run -w @prism3/tokens check:consumability`.
   - **Last, after the web build** — `npx tsx packages/engine/lint-us-english.ts` and `npx tsx packages/engine/lint-voice.ts`; their scope includes the built `apps/studio/dist/*.js` bundle, so running them earlier scans a stale one.

   **Full per-gate rationale — why each gate exists, what it caught, how it verifies independent of its subject — lives in `CONTRIBUTING.md` §3 and each gate's own file header, not here.** `lint-doc-gates.ts` fails CI if this list, `CONTRIBUTING.md` §3, or the PR template drifts from `ci.yml`.

   **A gate is only as strong as the independence of the two things it compares.** A gate whose expected value is derived from the thing it checks cannot fail — and it reports that as a pass, not as silence. **So the check is not "does the suite go red" — it is: mutate the subject and confirm *your* gate is among the failures, by name.** DRY between a gate and its subject is a *silent deletion of the gate*, not a cleanup, and a gate's scope must assert each promised surface is **represented**, never merely count files. This is the most-repeated defect class in the repo's history and not one instance was ever caught by a gate — every one was found by hand. Read `docs/34-gate-independence.md` (the rule, the sub-shapes, and the register) *before* writing a gate, not after.

5. **Versioning: names are versioned, values are not.** Two independent versions live in `packages/engine/version.ts`. `ENGINE_VERSION` answers *"what code produced this?"* — stamped into every emitted tree's `$extensions.generator.version` and reported as the MCP `serverInfo.version`; it bumps on any behavior change including a pure value change. `CONTRACT_VERSION` answers *"can my app still resolve the names it references?"* — it bumps **only** when the guaranteed token-name surface moves. The split is the point: a consumer hard-codes `prism.color.text.primary` and does not care that the brand's hue moved four degrees, but a rename makes that reference resolve to nothing with no error anywhere. `packages/engine/schema/token-contract.json` is the committed baseline, keyed *below* the configurable root because the root is itself a lever. Removing or retyping a path is MAJOR; adding is MINOR; `brandDependent` paths never force a bump. **Never add this baseline to `regen.ts`** — regen rewrites every generated artifact, so a regenerated baseline would silently rewrite itself to agree with a deletion and both gates would go green. It is rewritten only by an explicit `npx tsx packages/engine/token-contract.ts --accept`, which refuses unless `CONTRACT_VERSION` has already been raised by the increment the diff requires: **a gate allowed to rewrite what it reads has no memory.** Full policy, corpus rationale and what is deliberately *not* covered: `docs/30-versioning-and-compatibility.md`.
